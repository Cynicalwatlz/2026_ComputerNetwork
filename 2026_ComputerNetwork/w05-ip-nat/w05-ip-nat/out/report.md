# w05-ip-nat Task 2 보고서

## A. IP 주소와 서브넷

### A2. Wi-Fi 환경의 주소 정보

- 사설 IPv4 주소: `192.168.35.69/24`
- 기본 게이트웨이: `192.168.35.1`
- 외부에서 확인한 공인 IPv4 주소: `1.247.57.238`

`/24`는 서브넷 마스크 `255.255.255.0`을 뜻한다. 따라서 네트워크 주소는 `192.168.35.0`, 브로드캐스트 주소는 `192.168.35.255`이고, 일반 호스트가 사용할 수 있는 범위는 `192.168.35.1`부터 `192.168.35.254`까지이다. 측정된 호스트 주소와 게이트웨이는 모두 이 범위에 속한다.

### A3. 모바일 핫스팟 환경의 주소 정보

- 사설 IPv4 주소: `10.165.56.227/24`
- 기본 게이트웨이: `10.165.56.93`
- 외부에서 확인한 공인 IPv4 주소: `223.39.177.60`

이 환경도 `/24`이므로 네트워크 주소는 `10.165.56.0`, 브로드캐스트 주소는 `10.165.56.255`이며, 사용 가능한 호스트 범위는 `10.165.56.1`부터 `10.165.56.254`까지이다. Wi-Fi에서 핫스팟으로 접속망을 바꾸자 사설 주소, 게이트웨이, 공인 주소가 모두 바뀌었다.

### A4. WSL 주소와 서브넷

- WSL IPv4 주소: `172.21.94.128/20`
- WSL 기본 게이트웨이: `172.21.80.1`

`/20`의 서브넷 마스크는 `255.255.240.0`이며, 세 번째 옥텟이 16 단위로 구분된다. `94`는 `80~95` 구간에 있으므로 네트워크 주소는 `172.21.80.0`, 브로드캐스트 주소는 `172.21.95.255`, 사용 가능한 호스트 범위는 `172.21.80.1`부터 `172.21.95.254`까지이다.

### A5. 접속망 변경 결과의 비교

Windows의 물리 Wi-Fi 주소는 접속한 네트워크가 제공하므로 Wi-Fi에서 핫스팟으로 바꾸었을 때 `192.168.35.69`에서 `10.165.56.227`로 바뀌었다. 기본 게이트웨이와 공인 주소도 함께 바뀌어, 인터넷으로 나가는 물리 경로가 달라졌음을 보여 준다.

반면 WSL의 주소 `172.21.94.128/20`과 게이트웨이 `172.21.80.1`은 바뀌지 않았다. WSL은 Windows가 만든 별도의 가상 사설망에 연결되기 때문에, 바깥쪽 물리 네트워크가 바뀌어도 내부 가상망 주소는 그대로 유지될 수 있다.

> 측정 시 사용한 스크립트는 물리 Windows Wi-Fi 인터페이스가 아니라 WSL 내부의 주소와 게이트웨이를 수집했다. 따라서 Windows의 `192.168.35.69` 및 `10.165.56.227` 값은 Windows 측에서 따로 확인한 측정값이며, 스크립트 출력만으로 얻은 값은 아니다.

## B. NAT 관찰

### B3. 사설 주소와 공인 주소의 관계

Wi-Fi에서는 내부 주소 `192.168.35.69`가 인터넷에서 `1.247.57.238`로 보였고, 핫스팟에서는 내부 주소 `10.165.56.227`이 `223.39.177.60`으로 보였다. 사설 주소는 인터넷에서 직접 라우팅되지 않으므로, 각 접속 경로의 NAT 장치가 출발지 주소(필요하면 포트도 포함)를 공인 주소로 변환해 통신하게 된다. 이 결과로 하나의 공인 주소를 여러 내부 장치가 공유할 수 있다.

측정으로 확실히 말할 수 있는 것은 물리적인 인터넷 경로에 NAT가 최소 한 번 존재한다는 점이다. 다만 이 자료만으로 전체 NAT 단계의 정확한 개수를 단정할 수는 없다. WSL 트래픽은 먼저 WSL 가상망에서 Windows 쪽으로 변환되는 가상 NAT를 한 번 더 거칠 수 있으므로, WSL에서 시작한 패킷에는 NAT 단계가 추가될 가능성이 있다.

## C. DHCP 패킷 분석

### C2. 주소 할당 순서

캡처된 새 주소 할당 과정은 다음과 같다.

| 패킷 번호 | DHCP 메시지 | 출발지 | 목적지 | 의미 |
|---:|---|---|---|---|
| 4 | Discover | `0.0.0.0` | `255.255.255.255` | 주소가 없는 클라이언트가 DHCP 서버를 찾는다. |
| 5 | Offer | `192.168.35.1` | `255.255.255.255` | 서버가 사용할 주소와 설정을 제안한다. |
| 6 | Request | `0.0.0.0` | `255.255.255.255` | 클라이언트가 제안받은 주소를 요청한다. |
| 7 | ACK | `192.168.35.1` | `255.255.255.255` | 서버가 임대를 최종 승인한다. |

이는 DHCP의 일반적인 `Discover → Offer → Request → ACK`(DORA) 절차와 일치한다. 아직 주소를 받지 못한 클라이언트는 출발지로 `0.0.0.0`을 사용하고, 서버 위치와 네트워크 설정을 확실히 알기 전이므로 브로드캐스트 `255.255.255.255`로 메시지를 보낸다. 서버 응답도 캡처에서는 브로드캐스트로 전달되었다.

### C3. Transaction ID의 역할

네 패킷의 transaction ID는 모두 `0xe70ba322`이다. DHCP 메시지는 브로드캐스트로 오갈 수 있으므로 같은 네트워크에 여러 클라이언트의 교환이 섞일 수 있다. 클라이언트와 서버는 이 값을 사용해 Discover, Offer, Request, ACK가 하나의 주소 할당 절차에 속한다는 것을 연결한다.

### C4. 임대 시간과 갱신 시점

캡처에서 확인된 IP address lease time은 `3600초`, 즉 1시간이다. DHCP 옵션으로 별도의 T1 갱신 시간이 주어지지 않았다고 가정하면 기본 T1은 임대 시간의 50%이므로 `1800초`, 즉 30분 뒤이다. 이때 클라이언트는 보통 현재 DHCP 서버에 임대 갱신을 요청한다. 단, 패킷에 Renewal Time Value(Option 58)가 명시되어 있다면 그 옵션 값이 기본 계산보다 우선한다.

## 결론

접속망을 변경하면 Windows가 받은 사설 주소와 게이트웨이, 외부에서 보이는 공인 주소가 모두 달라졌다. 반면 Windows 내부의 가상망을 사용하는 WSL 주소는 유지되었다. 또한 DHCP 캡처에서 동일한 transaction ID를 가진 DORA 네 패킷과 1시간의 임대 시간을 확인했으며, NAT 단계의 정확한 개수는 추가 경로 측정 없이는 확정하지 않았다.
